## ADDED Requirements

### Requirement: Dictionary build emits SQLite artifact and enrichment-meta side file
The build tool SHALL produce a `dictionary.sqlite` containing all entries and surface-form index data. Entries without Russian translations have no rows in the `translations` table; the file is deployable as-is without running enrichment. The build SHALL also emit `enrichment-meta.jsonl` — a build-machine support file containing senses context and priority data for the enrichment tool. `enrichment-meta.jsonl` is NOT shipped to clients.

#### Scenario: SQLite artifact is created
- **WHEN** the dictionary build runs
- **THEN** a file named `dictionary.sqlite` is written to the build output directory
- **AND** the file contains a `lemmas` table (with `text_id`, `value`, `pos`, `rank`) and a `translations` table
- **AND** lemmas without Russian translations have no rows in the `translations` table
- **AND** a file named `enrichment-meta.jsonl` is also written to the build output directory

### Requirement: Translation enrichment is optional and applied in-place
The enrichment pipeline is a separate, optional step that patches an existing `dictionary.sqlite` with Russian translations. The build output is deployable before enrichment runs.

The enrichment tool SHALL query `dictionary.sqlite` for untranslated lemmas (those absent from the `translations` table), load senses context from `enrichment-meta.jsonl`, call a translation API, and write results to a durable side-file `enrichment-output.jsonl`. A separate `apply-enrichment!` step applies the side-file to `dictionary.sqlite` using gap-fill semantics: only lemmas with no existing translations are patched. Kaikki-sourced translations are never overwritten.

`enrichment-output.jsonl` is the authoritative translation record. If `dictionary.sqlite` is rebuilt from kaikki, the patch can be reapplied without re-running the translation API. `enrichment-meta.jsonl` is regenerated by the build and does not need to survive kaikki rebuilds.

#### Scenario: Untranslated lemmas are queried from the database
- **WHEN** the enrichment tool runs
- **THEN** it queries `dictionary.sqlite` for lemma rows absent from the `translations` table
- **AND** loads senses context and priority data for those lemmas from `enrichment-meta.jsonl`
- **AND** does not depend on a separately emitted `enrichment-input.jsonl` file

#### Scenario: Enrichment output is written to a side-file
- **WHEN** the enrichment tool receives translations from the API
- **THEN** it appends `{id, translation}` records to `enrichment-output.jsonl`
- **AND** the file persists independently of any subsequent kaikki rebuild

#### Scenario: Apply-enrichment patches with gap-fill semantics
- **WHEN** `apply-enrichment!` runs against `dictionary.sqlite` with `enrichment-output.jsonl`
- **THEN** it INSERTs translation rows only for lemmas absent from the `translations` table
- **AND** lemmas already having kaikki-sourced translations are not modified
- **AND** the entire apply runs in a single transaction
- **AND** patch records whose `text_id` is absent from the database are silently skipped

#### Scenario: surface_forms table has covering index
- **WHEN** the SQLite artifact is inspected
- **THEN** `surface_forms` has an index on `normalized_form`
- **AND** a query `SELECT lemma_id FROM surface_forms WHERE normalized_form = ?` uses the index

### Requirement: Duplicate Kaikki entries are merged by [word, pos, discriminant] key

The build tool SHALL merge multiple Kaikki source entries that share the same word, part-of-speech, and discriminant into a single lemma by unioning their senses, translations, and inflected forms.

The discriminant is derived from entry-level tags: sorted gender tags for nouns (`masculine`, `feminine`, `neuter`), separability tag for verbs (`separable`, `inseparable`), or nil when no such tag is present.

Entries that share the same key but are etymologically distinct homographs (e.g. *der Abort* toilet/miscarriage, *abhängen* to-depend/to-take-down) SHALL be merged into a single lemma. This is a known limitation of the source data: the Kaikki dump does not include `etymology_number`, making these homographs indistinguishable at build time.

#### Scenario: duplicate entries are merged
- **WHEN** the build processes two Kaikki entries with identical `[word, pos, discriminant]`
- **THEN** the resulting lemma contains the union of both entries' senses, translations, and forms

#### Scenario: homographs with different discriminants are kept separate
- **WHEN** two entries share word and pos but differ in discriminant (e.g. `die See` vs `der See`)
- **THEN** they are emitted as separate lemmas with distinct IDs

### Requirement: Server serves versioned SQLite file
The server SHALL expose the dictionary SQLite artifact at `GET /dictionary/v{epoch}` with gzip encoding and a content-hash header.

#### Scenario: File is served with correct headers
- **WHEN** a client requests `GET /dictionary/v{epoch}`
- **THEN** the response has `Content-Encoding: gzip`
- **AND** the response includes an `ETag` or `X-Content-Hash` header derived from the file content

#### Scenario: Unknown version returns 404
- **WHEN** a client requests a version that does not exist
- **THEN** the server responds with HTTP 404

### Requirement: Dictionary Worker opens SQLite via OPFS
The client SHALL include a Web Worker that downloads the versioned SQLite file, writes it to OPFS using `SyncAccessHandle`, and opens it with sql.js for query execution.

#### Scenario: Worker initialises on first boot
- **WHEN** the Worker starts and no OPFS file exists for the current version
- **THEN** the Worker downloads `dict.v{epoch}.sqlite` from the server
- **AND** writes it to OPFS
- **AND** opens the database with sql.js
- **AND** posts a `{type: "ready"}` message to the main thread

#### Scenario: Worker uses cached file on subsequent boots
- **WHEN** the Worker starts and the current-version file already exists in OPFS
- **THEN** the Worker opens the existing OPFS file without re-downloading
- **AND** posts a `{type: "ready"}` message to the main thread

#### Scenario: Atomic version swap on epoch bump
- **WHEN** the Worker detects a new epoch from the server
- **THEN** it writes the new `dict.v{new}.sqlite` to OPFS fully before switching
- **AND** deletes the old `dict.v{old}.sqlite` after the new file is successfully opened
- **AND** if the download is interrupted, the old version remains open and functional

### Requirement: dictionary.cljs routes lookups through Worker
The `attach-translations` and `suggest` functions in `dictionary.cljs` SHALL delegate to the Worker via `postMessage` and return results via promise or callback, preserving the existing call signatures.

#### Scenario: attach-translations resolves via Worker
- **WHEN** `attach-translations` is called with a list of surface forms
- **THEN** a message is posted to the dictionary Worker
- **AND** the function returns results equivalent to the previous PouchDB-backed implementation

#### Scenario: suggest resolves via Worker
- **WHEN** `suggest` is called with a prefix string
- **THEN** a message is posted to the dictionary Worker
- **AND** the function returns a ranked list of matching surface forms

### Requirement: dictionary PouchDB path is removed
After Phase 2 is stable, the system SHALL NOT initialise `dictionary-db` in PouchDB, and `dictionary-sync.cljs` SHALL NOT replicate dictionary documents.

#### Scenario: dictionary-db is absent from dbs initialisation
- **WHEN** the client application boots
- **THEN** no PouchDB database named `dictionary-db` (or equivalent) is created or opened

#### Scenario: dictionary-sync does not replicate dictionary documents
- **WHEN** the sync cycle runs
- **THEN** no CouchDB replication is attempted for dictionary entries or surface forms
